# 3. Workflow anatomy

**Applies when:** The repo is on GitHub Actions and its workflow lacks a plan job that gates the others, or a single result job that checks them. **Skip when:** The workflow already gates every job on a plan and checks them in one result job.

One main workflow, shaped as **plan → jobs → result**:

- **Plan job** (2 vCPU, no workspace install). It reads the diff and writes outputs: which test files, the shard split, which jobs, the runner size, and whether to pack, build Rust or run proofs. It logs its inputs and selection, so every run can be audited later.
- **Every other job is `if:`-gated on the plan's outputs.** A job the plan didn't select is skipped and costs nothing.
- **One aggregate result job** runs `if: always()`. It checks that every job the plan selected succeeded, every work-stealing batch had an owner, and the review record is valid. A skipped job counts only if the plan didn't select it. It checks both directions of the plan's mapping on every run: every job the plan can select is in its `needs`, and every job in `needs` is one the plan can select. Otherwise a job left out of `needs` passes unseen on the run that selects it, and one the plan never selects passes whenever it's skipped. A missing or malformed plan output fails it. The template keeps the list once, as `SELECTABLE_JOBS`.
  - **GitHub accepts a skipped job as a passing required check.** Our result job skips on drafts, so "required" alone doesn't stop a merge of a draft-time head. Our merge process requires a successful, non-skipped `CI result` from the ready run on the current tested revision, enforced by the merger. Either do the same, or make the gate report an explicit blocking conclusion. If the repo uses a merge queue, the workflow also needs a `merge_group` trigger. ([GitHub's required-check behaviour](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks).)
  - **Cut over in steps.** Inventory the current rulesets, required check names, apps, merge methods and merge queue first. Run the new gate beside the existing ones; check it on ready heads, ready-after-draft, a missing selected job, a failure, a cancellation and, if enabled, `merge_group`. Switch the required checks only in an approved cutover with a rollback.
- **Wait instead of `needs` where it helps.** A small composite action polls the latest attempt of a named job, or a named *step*, every 5 s, and fails at once if the prerequisite fails. Downstream jobs start setup in parallel and wait only for the artifact they need. It pays for the waiting job's runner from its start, so use it only where the artifact really becomes ready before its job ends and a model shows the overlap beats the idle cost and queueing; otherwise keep `needs`.
- **Composite actions** handle dependency and toolchain setup, and builds that several callers share. The templates bundle them as local actions (`./.github/actions/<name>`). We keep ours, and a few reusable workflows, in a shared repo **pinned by full commit SHA**, updated in a PR of their own so CI tests the change alone; that's a deployment choice, not something the templates need.
- **Per-job `timeout-minutes` and measured budgets** (section 12). A CI test fails if a reachable job has no budget.
- **Concurrency groups** are split by event (section 4).
- **Small controller workflows** handle the schedules: sweep, bisect, health, startup watch, infra drift, load baseline and latest-tool checks. Each runs on 2 vCPU with serialized concurrency, and dispatches the main workflow with inputs rather than duplicating it.
- **Manual dispatch inputs** for narrow runs: exact ref, test paths, one container file, name filter and repeat count. Two revisions are in play: `gh workflow run ci.yml --ref <branch> -f ref=<branch>` picks the workflow's revision with `--ref` and the tested code with the `ref` input. Without `--ref`, a branch behind main fails on main's newer workflow scripts.
- **Explicit dispatch between workflows.** Pushes made with the Actions token don't trigger workflows, and `workflow_run` chains proved unreliable, so a workflow that must start another dispatches it explicitly.
- **A late review record doesn't rerun CI.** A separate small workflow reruns only the result job when a valid review record lands after the result failed for that reason alone.
- **CI edits are diffed as YAML** (section 4), so editing one job runs that job and its dependents, not everything.
