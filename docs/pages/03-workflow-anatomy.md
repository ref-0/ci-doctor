# 3. Workflow anatomy

**Applies when:** The repo is on GitHub Actions and its workflow lacks a plan job that gates the others, or a single result job that verifies them. **Skip when:** The workflow already gates every job on a plan and checks them in one result job.

We run one main workflow shaped as **plan → jobs → result**:

- **Plan job (2 vCPU, no workspace install).** Reads the diff and emits outputs: which test files to run, the shard split, which jobs to enable, the runner size, and whether to pack, build Rust, or run proofs. It logs its inputs and selection so every run can be audited later.
- **Every downstream job is `if:`-gated on the plan's outputs.** Any job the plan doesn't select is skipped and costs nothing.
- **One aggregate result job (`if: always()`).** Verifies that every selected job succeeded, every work-stealing batch had an owner, and the review record is valid. A skipped job passes only when the plan did not select it, and a missing or malformed plan output fails the run.
  - **Check both directions of the job map on every run:** every job the plan can select must appear in the result job's `needs`, and every job in `needs` must be one the plan can select. Otherwise, a job omitted from `needs` can fail unseen when selected, and an unselectable job passes whenever it's skipped. The template stores this list in one place as `SELECTABLE_JOBS`.
  - **GitHub treats a skipped required check as passing.** Because our result job skips on drafts, marking it "required" alone won't block merging a draft-time head. Our merge process requires a successful, non-skipped `CI result` from the ready run on the current tested revision, enforced by the merger. Either enforce the same rule or have the gate report an explicit blocking conclusion. If the repo uses a merge queue, add a `merge_group` trigger as well ([GitHub's required-check behaviour](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)).
  - **Cut over in steps.** First inventory existing rulesets, required check names, apps, merge methods, and merge queues. Run the new gate alongside the existing ones and test it on ready heads, ready-after-draft, a missing selected job, a failure, a cancellation, and (if enabled) `merge_group`. Switch required checks only in an approved cutover with a rollback plan.
- **Wait instead of `needs` only where overlap pays off.** A small composite action polls the latest attempt of a named job—or a named *step*—every 5 s, failing immediately if the prerequisite fails. This lets downstream jobs run setup in parallel and wait only for the artifact they need. Because the waiting job bills its runner from the moment it starts, use this only when the artifact becomes ready well before its upstream job ends and a model shows the overlap beats idle cost and queueing; otherwise stick with `needs`.
- **Composite actions** handle dependency setup, toolchain setup, and shared builds. The templates bundle them as local actions (`./.github/actions/<name>`). We keep ours (along with a few reusable workflows) in a shared repo **pinned by full commit SHA**, updated in dedicated PRs so CI tests each change in isolation—a deployment choice, not a requirement of the templates.
- **Per-job `timeout-minutes` and measured budgets** (section 12). A CI test fails if any reachable job lacks a budget.
- **Concurrency groups** are split by event (section 4).
- **Small controller workflows** drive scheduled work: sweep, bisect, health, startup watch, infra drift, load baseline, and latest-tool checks. Each runs on 2 vCPU with serialized concurrency and dispatches the main workflow with inputs rather than duplicating its logic.
- **Manual dispatch inputs** support narrow runs: exact ref, test paths, a single container file, name filter, and repeat count. Remember that two revisions are in play: `gh workflow run ci.yml --ref <branch> -f ref=<branch>` selects the workflow definition with `--ref` and the code under test with `-f ref`. Omitting `--ref` causes a branch behind `main` to run against `main`'s newer workflow scripts and fail.
- **Explicit dispatch between workflows.** Pushes made with `GITHUB_TOKEN` don't trigger workflows, and `workflow_run` chains proved unreliable, so any workflow that needs to trigger another dispatches it explicitly.
- **A late review record doesn't rerun CI.** A small separate workflow reruns only the aggregate result job when a valid review record arrives after the result failed solely for missing it.
- **CI edits are diffed as YAML** (section 4), so editing one job runs only that job and its dependents, not the whole pipeline.
