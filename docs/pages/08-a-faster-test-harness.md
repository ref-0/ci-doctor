# Test harness

Cut the time and work a heavy test runtime, such as workerd under Vitest, adds to each test file, without making any test prove less.

**Applies when:** A server with a heavy runtime per test file, such as workerd under Vitest. **Skip when:** The runtime's startup and bundling are a small share of each test file's time.

Our server ran on Cloudflare Workers, so its tests ran it in workerd under Vitest. The ideas apply to any server with a heavy runtime per test file; what was specific to Workers is in the [`speed-up-tests`](../../skills/speed-up-tests/SKILL.md) skill's [Workers page](../../skills/speed-up-tests/references/workers.md), if your stack runs on them. A coding agent making a slow test faster follows that skill.

- **Bundle the server once per input state.** Build a Wrangler dry-run bundle with a metafile and reuse it until its real inputs change, rebuilding under a file lock and publishing atomically. Each file still gets its own runtime. Locally this cut most of each harness's bundling CPU and about 50 MB of writes, and a generated one-line entry avoided reparsing a ~12 MB bundle. In CI, mean harness copy-and-start fell to about 40% of its old time.
- **Time the harness's start by phase before you share anything.** A temporary log of each phase, on a throwaway branch, split one start into parsing the entry, serializing the runtime's config, the runtime's own start and the database copy. Two of them were waste: the wrapper parsed the whole bundle only to guess its format (the one-line entry above), and the runtime's config encoder grew its buffer one small step at a time (patched to double). The database copy needed nothing from the runtime, so it now runs while the runtime starts, and the harness reports ready only once both are done. Those three changes together are the 40% above, with every file still on its own runtime: what was left was mostly the runtime itself.
- **A cache restore is a writer too.** Files whose fixtures built another app raced while one file's build emptied its output folder, and a cache hit rewrote the same files in place (delete, then create) while another file's runtime still served them. A lock alone didn't help, because readers hold the path long after the lock is released. Each build now runs under the lock, copies its whole output to a folder named by its content and hands readers that path, which nothing writes again. A small shared file, such as the bundle's config, is written beside its path and renamed onto it. After the fix the affected files passed together in each of six CI runs; we have no rate from before to compare.
- **Keep module load cheap, and gate it.** Work at import time is paid by every test file's runtime, every local dev start and every cold production instance. Profile the import alone: allocations at load, errors constructed, and CPU in the local runtime. Then move what isn't needed at load to first use. Holding the V8 stack-trace depth low while modules load, and restoring it before the first request, cut local start CPU by about 30%; deriving each endpoint's codecs on first use, and no longer importing a schema library the server never called, cut allocation at load by about 30%, both measured locally in the runtime, while the first request in an instance pays the derivation once. The static job gates both deploy bundles on **bytes allocated at load**, which repeat exactly, 15% over the measured value. CPU on CI's runners swung about 2× between runs, so it is only a gross ceiling there. A test-runtime timing is not a production one: measure the platform's own start separately (the [Workers notes](../../skills/speed-up-tests/references/workers.md#startup-at-module-load) say how).
- **A fixture that listens fails at once, with its reason.** Check the socket path's byte length before binding (107 bytes on Linux, 103 on macOS), make socket homes under a short root rather than a long `TMPDIR`, and listen for the server's `error` event, so a refused bind ends the setup instead of starting a wait. Before this, a long `TMPDIR` made fixtures wait out a 90 s test timeout each; after it, a forced bind failure returned in milliseconds. [Section 11](11-flakes.md#cause-symptom-fix) has the entry.
- **One Postgres, many databases.** One embedded Postgres per run serves every task, and each harness gets a database copied from a lazily migrated template, which takes milliseconds. Run it non-durable, give each run a unique port and directory, and reap only dead owners. Don't import the embedded-Postgres package's exit hook: it could turn a failed Vitest into exit 0.
- **Patch harness faults instead of retrying around them.**
  - A pinned Miniflare patch forces fresh connections where a blocked Node process can't retire idle sockets that workerd expires after 5 s.
  - A pinned HTTP-client patch fixed false "terminated" errors after all body bytes had arrived. The memory-ceiling "flakes" were really this transport bug.
- **Drain runtime output outside the test process,** so a full pipe can't stall startup.
- **A detached fixture server dies with its test process.** A server started in its own session escapes a process-group kill, and a killed test worker runs no finalizer. Give each one a pipe whose other end only the test process holds, and make the server exit on EOF: the kernel closes the pipe on any exit, `SIGKILL` included ([section 11](11-flakes.md#cause-symptom-fix)).
- **Watchdogs.** An external watchdog kills a blocked test thread after its timeout plus 10 s, because an in-process timer can't fire while the event loop is blocked. Container files get a 10-minute file budget, and no single test may ask for more than half of it.
- **Keep the system real and fake only the outside:**
  - **Real:** the runtime, its SQLite, Postgres and the pinned Git oracle.
  - **Fake:** external services, which answer at once.
  - **Network guard:** a default guard fails any request no fake answers.
