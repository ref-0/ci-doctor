# Measuring before and after

Part of the [`speed-up-tests`](../SKILL.md) skill. Read it before you rank files or quote a number in a pull request or a plan. This page owns where CI's records are and how to read them; for history collected from the API, read [CI history data](ci-history-data.md). How to judge any number, before and after, is [`prove-it`](https://github.com/ref-0/ci-doctor/blob/v0.4.0/skills/prove-it/SKILL.md): the decision and noise floor first, interleaved runs, the limiter, a control group's drift, what else it measured, and observed versus modelled. The rules below are only what's particular to tests and CI.

The records themselves: per-file times written by the test reporter into the job's log ([`scripts/records/`](https://github.com/ref-0/ci-doctor/blob/v0.4.0/scripts/records/README.md)), collected nightly and ranked; each job's start and end in the CI provider's jobs API ([`ci-time.ts`](https://github.com/ref-0/ci-doctor/blob/v0.4.0/skills/ci-workflows/scripts/ci-time.ts)); and, if you run on Blacksmith, its job records and CPU stats ([CLI](https://github.com/ref-0/ci-doctor/blob/v0.4.0/skills/blacksmith/references/cli.md)). The repo's own collector and paths are in `.agents/repo/speed-up-tests.md`.

## Reading CI's records

- **Time only passing, complete file runs.** Keep failed and cut-short runs for failure analysis, but leave them out of a file's median. Carry each observation's commit, run attempt and time.
- **Rank the newest passing runs in the window `speed-up-tests.md`'s Thresholds name** (five in the source repo), and print how many there were: flag a file with fewer than three, and don't call a thin or mixed-code sample a gain.
- **Rank two ways.** Total test-seconds says where the work is. The file that ends its shard last says what sets a run's wall time. One file of a few slow tests can matter more than a hundred quick ones, since a runner rarely splits a file.
- **Count only real runs.** A task a cache replays reprints old times. Read only records of what ran.
- **Say what the sample is:** the window, how many runs had records and which files were timed. If the records stop on a date, check the collector before you believe the quiet.
- **Shard count isn't full selection.** A run with many shards may still have selected a subset, or replayed most of it from a cache. Call a run full only when its plan's selected files match every eligible file at that commit, for ordinary, heavy and container tests separately, and report selected, executed and replayed counts apart. Until you have that, call it "a large run by shard count" and its total "fresh recorded test-seconds", never a whole-suite before/after.
- **Split a failure by commit before you call it a flake.** A failure on one branch alone is that branch's. A failure after a fix merged may have run the fix's parent: check that the run's commit holds the fix, and order attempts deterministically. A pull request's run, and each rerun of it, can test its merge into the base as the base stood when the run was first triggered, so a rerun hours after the fix merged may still test the old base: check the commit the failed job actually checked out, not the branch's tip.
- **Read the error, not the test's name.** A memory-ceiling test that failed with `TypeError: terminated` was a fetch library's bug, not memory.
- **Collect again after each round,** and leave out what has merged since.

## Comparing before and after

- **The same command, field and conditions on both sides.** A split compares per-file totals. A wait compares test time without the shared setup. Don't mix them.
- **Take a test file apart.** A small warm file's time splits into fixed process cost, harness start and its tests, and a rebuild of a bundle can add as much again. Locally, waits for a shared test slot can be most of a run. Measure the part you change.
- **Time the wait itself when the total is noisy:** when setup dominates a run, the waits can fall clearly while the total barely moves. A saving under a second a case is smaller than a whole file's swing on a loaded machine: read it from the case's own times in the job's records, or run the cases alone, interleaved.
- **A ceiling costs no time.** Reading code once overestimated a poll's cost several times over against its measurement: a ceiling, a hold the test cancels, a fake clock's age or a count of steps costs nothing. Overlapping fixes don't add up.
- **Compare at like hours, like days and on the same files.** A full run's total moves with the runners' hour and with the tests other changes add: afternoon runs took about half again as long as the same morning's, and a newest-five sum rose partly from new proof files. Compare a file with its own history. Days differ too: weekend runs ran below their files' medians, and the following weekdays' runs well above them. Divide a run by its speed factor, the median over its files of each file's time over that file's median, before comparing it. Then judge whether a file moved by its normalized median, its times each divided by their run's speed factor, against its earlier normalized one, and never by raw against normalized. Raw against raw reads the runs' load as the file's: over a weekend's mix of small runs in the source repo, 20 to 23 November 2026, it flagged 16 of 198 files as moved past 40%, where normalized against normalized flagged 2.
- **Measure a shortened bound before keeping it.** A bound the work ends before saves nothing: a deadline cut to a quarter still took a retry's whole interval, so that test ran with no wait instead. For a poll, run its interval A/B interleaved rather than counting its sleeps: the sleeps past their checks were under 2% of the files' time, and a fifth of the interval changed nothing.
- **Judge a file against its shard, and keep the raw number.** Shards in one run differ as wholes, by up to about half again their medians, while their neighbours on a runner explained almost none of it. A shard's ratio also moves when the file itself got faster, when the shard's mix changed or when a cache replayed more or less of it. So divide by it only as a labelled adjustment beside the raw comparison, and only when the mix and the replays held still. A file alone in its job has no shard to judge by: for a small effect, time each case, and take the cases the change leaves alone as the controls for the runner's speed, reported beside the raw times. In the source repo, on 20 November 2026, the untouched cases of one such job ran 1.4 to 2 times slower than before, which hid a halving seen locally.
- **Case sums are a lower bound.** A packer needs each file's whole elapsed time, collection and setup included. The sum of printed case durations leaves those out: if it exceeds an estimate, the estimate is low; if it's below, that proves nothing. Never replace estimates with case sums. A skipped file has no time.
- **Check a planner replay's baseline** against the real runs it models. For each workload, say which numbers were observed and which come from a replay or a model, and name the next normal run that will observe the rest; don't dispatch one to fill the gap.
- **A cache's replay rate isn't a saving.** Compare full runs with full runs, keep cold, partly reused and warm cohorts apart, and count the task runner's and test runner's start-up and the idle tail at each shard's end. Set the rollback criterion before adopting it.
- **Three numbers:** test-seconds summed over files, a run's wall time, which the slowest shard sets, and billed minutes, which round up each job's minutes times its vCPUs. A cache that saved seconds a job can barely move wall time, and a shared database that saved many lane-seconds can save almost no billed minutes.
- **A narrowed margin passes repeated runs with no retry,** and a mutation still fails it.
