# Phase 5: make it stay fast

With the user's approval of each part:

- **A spend limit first.** Start with a GitHub Actions budget and alerts the user owns, wherever their billing scope supports one ([GitHub's budgets](https://docs.github.com/en/billing/how-tos/set-up-budgets)). Record the scope, who can change it, and what stopping does: a budget set to stop usage blocks further metered usage, which can stop release, security or recovery workflows too. An external watcher such as [`scripts/budgets/`](../../../../scripts/budgets/README.md#3-the-spend-watcher)'s is a separate approval. It needs a reader for the user's own provider, an explicit list of the workflows it may disable, a dry-run or report-only default, a stop-and-recovery drill, and a documented human override before it's enabled.
- **Budgets, report-only first.** Run them against existing runs. Record the sample count and the job legs with no measurement, and tell a missing budget apart from an overrun. Wait for a minimum sample the user picks before enforcing. Configure job names, matrix and caller workflows, and runner prices first. Ask before turning on CI failure, issue writes or closures, or a daily schedule, and say what happens on a fork without write permission. Our budgets (a job's p95 + 15%, 5 minutes full and 3 minutes small, about 90 s a test file) are examples.
- **A daily health report** that keeps one issue open while over budget, once its writes are approved.
- **Flake issues** filed automatically and closed only after real clean runs, if the plan approved a retry policy and issue writes.
- **A runner review** that re-checks each job's runner against its measured CPU and memory and proposes resizes, as [`ci-runners`' sizing](../ci-runners/references/sizing.md#reviewing-sizes-on-a-schedule) says. Set its cadence from PR volume: daily when each job gets a fair sample of runs every day, weekly otherwise. Tests change, so a size that fit at the plan drifts.
- **A standing slow-tests and flakes run** on the agreed cadence, following guide section 15, with the same "may / propose / never" guardrails.
- **A follow-up for each main-only change,** as Phase 4 says. When a PR edits a job its own event can't run, the plan job prints a notice naming that job's tier and the branch dispatch that would test it (see [`templates/github/`](../../../../templates/github/README.md)); the follow-up reads the first eligible main run.
